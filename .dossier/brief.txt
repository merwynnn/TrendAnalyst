2 · How to work (senior-engineer standards)

    · Read the spec first -- Dossier 1 is law. If spec and instinct conflict, follow the spec and flag the conflict
to the human.

    · Track small tasks -- Keep a visible task list; exactly one item in progress; mark done only after
verification ran.

    · Typed Python always -- Type hints on every function, Pydantic models at every boundary (config,
plugin I/O, gate schemas).

    · Tests with every module -- No live network in tests -- recorded fixtures with secrets redacted. A new
source ships with its fixtures.

    · Verify by running -- After each phase: run pytest, the linter, and the real CLI path for what you built.
Paste or log the evidence; never claim green from memory.

    · Small diffs -- One phase at a time, each independently working. Never rewrite two layers in one go.
    · No secrets, ever -- Nothing credential-like in code, logs, fixtures, or docs. If you almost commit one,
stop and rotate the pattern, not just the value.
    · Stop on ambiguity -- Escalate to the human when: a spec invariant blocks you, an external API
contradicts the docs, a destructive action is the only path, or evals and judgment disagree twice in a row.

4 · Agent-engineering rules (distilled, enforced)

Drawn from current production practice (Anthropic 2025-2026: simple composable patterns, evaluator-
optimizer, orchestrator-workers, LLM-judge evals; LangGraph 2026: checkpoint-every-transition, replay
determinism, ledgers outside the rollback surface). Applied here as:

    · Workflows over agents -- The pipeline is fixed-path code, not an agent loop. LLM calls are single-shot
gates with schemas.

    · Orchestrator-workers only where subtasks are unpredictable -- Permitted inside the Writer gate
(angles per category). Nowhere else in v1.

    · Evaluator-optimizer for briefs -- Writer drafts, a narrow critic pass checks rubric items (citations,
ranges not points, risks present), one revision max.

    · Tools are UI -- Each plugin and each gate tool gets one purpose, a clear description, an example, and
its budget in code. If two tools overlap, merge them.

    · Scale effort to complexity -- Hard caps everywhere: max candidates per gate, max enrich calls per
night, max one Writer revision. Effort budgets live in config, not prompts.

    · Evals before features -- A behavior change without a golden case proving the old behavior is a
regression risk, not progress.

    · Checkpoint plus external ledger -- Resume-safe by construction (spec section 5). Test the kill-and-
resume path, not just the happy path.

    · Human interrupt for the irreversible -- Anything destructive, spend-increasing, or schema-changing
proposes and waits. The monitor agent inherits this (AGENT.md).

    · Context hygiene -- Tool outputs are truncated with sensible defaults; state stores references and
hashes, never blobs. Prompts receive slices, not lakes.

5.2 Required sections

    · Role and persona: careful SRE junior, evidence-first, proposes before acting outside the safe list.
    · Monitor loop procedure: read health, classify (healthy / degraded / down), match a runbook, act within
tier, verify, log, escalate with the exact template.
    · Five runbooks minimum: HTTP 429 storm from a source; source approval/schema change breaking a
plugin; quota burn above 80 percent; judge keep-rate drift outside band; eval baseline drop.
    · Change classes with examples: SAFE (restart from checkpoint), APPROVAL (disable flaky source for 7
days), FORBIDDEN (manual snapshot edits) -- each with verification step.
    · Escalation template: symptom, evidence (commands plus output), attempted safe actions, proposed
approval-class change, blast radius if ignored.
    · Rollback rule: every change you make MUST be reversible in one command, stated in the log line.

6 · USER_SETUP.md requirements (you MUST write this file)

USER_SETUP.md is the human action list. The human is non-technical here: every item needs where to click,
what to paste where, what it costs, and how to verify. Structure:

    · Key table with one row per credential: purpose, where to create it (exact console URL pattern), free tier
limit, where to put it (.env key name), verify command and expected output.

    · Accounts and approvals to file on day one, with expected wait times and what to do meanwhile (build
never blocks on approvals: sources start disabled).

    · Scheduler setup: the exact cron entry or Actions workflow to enable, plus how to trigger a manual run.
    · First-run checklist in order, ending with the health command and what healthy output looks like.
    · Cost summary table proving $0/month at expected volume, per provider, with the cap that would trigger
each paid tier.
    · Troubleshooting: the five most likely setup failures (bad key, wrong region, OAuth expiry, quota zero-day,
Postgres connection) with fix per failure.

Test of truth. If the human cannot go from zero to a green health check using only USER_SETUP.md,
the document -- and therefore your build -- is not done.

7 · Anti-patterns (any of these fails review)

    · Framework-first: importing an agent framework before the plain-code pipeline works.
    · LLM in the hot loop: any gate seeing unpruned L0 volume.
    · Tier-A in L0, or any network call without timeout, retry, budget and ledger entry.
    · Overwriting snapshots or mutating history to fix a bug -- append a correction, never rewrite.
    · Prompt-only budgets or unenforced grounding ("the prompt says to cite").
    · Live network in tests, secrets in fixtures, unpinned dependencies.
    · Silent failure: an exception path that logs nothing and continues as if healthy.
    · A swarm of agents where a checklist would do. Complexity MUST cite a measured need.
