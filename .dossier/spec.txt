1 · Purpose and non-goals

Purpose

Trend Analyst is a standalone Python system that (a) discovers underserved product gaps across physical
goods, digital goods and micro-SaaS (Discovery Engine), and (b) validates a user-supplied idea with a risk
score and a P10/P50/P90 revenue range (Validation Engine). It learns across runs: every nightly run appends
versioned snapshots instead of recomputing the world, and LLM judgment is applied only at three gates so
free-tier quotas survive.

Non-goals for v1

    · No sub-hour real-time alerting. Nightly batch plus one hourly lightweight poll is the ceiling.
    · No paid data APIs anywhere in the automated path. Manual browser spot-checks only.
    · No multi-user SaaS, no auth system, no billing. Single operator: you.
    · No heavy agent framework (LangChain / LangGraph) in v1. The pipeline is deterministic code with
checkpoints; the LLM is a tool with budgets, not the control flow. Revisit only with measured need.

4 · Source plugin architecture (the modularity core)

4.1 Plugin contract

what makes endpoints addable, removable and movable without touching pipeline code.

budget_per_day: int; rps: float; cache_ttl_h: int

5 · Execution and state (never redo work)

5.1 Run ledger and watermarks

Every run writes a ledger row per (run, layer, source): status, item counts, quota spent, timestamps. Each
source keeps a watermark (cursor or last-fetch timestamp). A rerun processes only what changed since the
watermark.

5.2 Content-hash dedup

Fetched payloads are normalized then hashed (SHA-256). Identical hash to the stored one means skip
parsing, skip scoring, skip LLM. This single mechanism is what keeps nightly runs near 10 minutes and LLM
calls near 50.

5.3 Append-only snapshots

Scores are versioned rows (candidate, run_id, weights_version, five sub-scores, fad probability, revenue
triple). History is never updated in place. Trends, backtests and weight learning all read the snapshot table.

5.4 Checkpoints, resume, TTL

    · Checkpoint after every layer per candidate batch. A crashed L2 resumes unfinished candidates only.

    · Raw lake rows expire after 90 days (TTL job). Snapshots and the ledger never expire.
    · Determinism check: replaying a checkpoint with identical inputs MUST reproduce identical downstream
scores (hash-asserted in CI).

    Critical rule. Side effects (quota spend, external writes) MUST be recorded in a ledger table the
    checkpoint system does not own, applied with compare-and-swap. A resume MUST be physically unable
    to double-spend quota or double-emit. State that must survive a rollback lives outside the rollback surface.

6 · Scoring and LLM gates

6.1 Gap score (computed in code, never by the LLM)

MGS = 0.30·DV + 0.25·(100"SS) + 0.20·SP + 0.15·MP + 0.10·FE. All inputs are per-category percentiles
computed in SQL/Python. The fad flag (30d vs 90d vs 365d slope divergence, seasonal strength, evergreen
ratio) is a classifier feature set, not a vibe. Revenue is Monte Carlo over TAM × CTR × CVR × price, reported
as P10/P50/P90.

6.2 The three gates (only LLM call sites in v1)

Gate              Job                                                            Budget

Planner (weekly)  User prompt -> search plan: keywords, sources, per-source      ~1 call
                  budgets

Judge (nightly)   Keep/drop + fad probability + enrich list, JSON, cited quotes  Batched, ~20 calls

Writer (nightly)  One-page brief: verdict, players, risks, angles, revenue       ~30 calls, top-K only
                  reasoning

6.3 Gateway, cache, schemas

    · Provider chain with automatic failover: Gemini Flash -> Groq -> Cerebras -> local Ollama. Per-gate call
and token caps; on cap, the gate degrades (skip with reason logged), never retries blindly.

    · LLM cache keyed by hash of normalized input, 30-day TTL. Identical work never hits a provider twice.
    · All gate outputs are Pydantic-validated JSON. Schema violation means retry once, then drop with
reason.
    · Grounding enforced in code: any factual claim without quote plus URL is stripped before it reaches
scores or briefs.

8 · Evals and CI (quality gate)

    · 50 golden cases in evals/cases.yaml: input signals plus expected keep/drop, fad label, and score band.
    · Single LLM-judge call per case scoring 0.0-1.0 plus pass/fail on: factual accuracy, citation accuracy,
completeness, source quality, tool efficiency.
    · Replay determinism: checkpoint replay MUST reproduce scores (hash match) or CI fails.
    · Release rule: no rubric may drop more than 2 points from baseline on any PR. Evals run in CI before
features merge.

9 · Observability and ops

    · Structured logs with run_id on every line. Token accounting per gate per run.
    · A health CLI (python -m trend_analyst.health) printing: last run status, per-source ok/degraded/down,
quota burn vs budget, judge keep-rate, eval baseline. The monitor agent reads this, not raw logs.
    · Alert thresholds: HTTP 429 rate, keep-rate drift beyond band, quota burn above 80 percent, eval drop.
Alerts go to a local outbox file the monitor agent triages.

10 · Security and configuration

    · pydantic-settings layered config: defaults < YAML < environment < CLI. Sample values only
in .env.example.

    · Secrets (API keys, tokens) live in environment or a local untracked file. NEVER in the repo, logs,
snapshots, or eval fixtures. Tests use recorded fixtures with secrets redacted.

    · Network egress allowlist derived from the registry: a source may only call its declared domains.
    · The monitor agent runs with least privilege: read plus explicitly listed safe actions (full matrix in
AGENT.md).
